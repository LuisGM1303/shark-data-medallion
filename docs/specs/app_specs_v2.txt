Software Architecture Specification (SAS)
=========================================

Shark Knowledge — Databricks-Centric Medallion Architecture
Version 2.0
Date: 2026-09-30
Status: Architecture Baseline / Data-Ready Target


1. PURPOSE
==========

This specification defines the target architecture for the evolution of Shark Knowledge
from a local-first Python implementation to a Databricks-centric lakehouse implementation.

The primary objective of version 2.0 is to preserve the validated business behavior of
the existing Python project while replacing local persistence and retrieval infrastructure
with native Databricks capabilities.

The immediate implementation goal is DATA READY:

    External APIs
        -> Bronze Delta
        -> Silver Delta
        -> Gold Delta

The planned future evolution is:

    Gold SpeciesChunks
        -> Databricks AI Search Delta Sync Index
        -> Knowledge Assistant

Knowledge Assistant is explicitly NOT part of the first implementation milestone of v2.


2. BACKGROUND AND CURRENT STATE
===============================

------------------------------

The current project is a complete local Python implementation of a medallion-style
knowledge ingestion pipeline for shark species.

The existing flow is:

    GBIF Species Match ---------+
    GBIF Occurrence Search -----+--> Bronze JSON
    Wikipedia ------------------+
                                      |

                                      v
                                     Gold

The implementation uses:

- Python 3.11+

- requests
- DuckDB
- sentence-transformers
- BAAI/bge-small-en-v1.5
- FAISS IndexHNSWFlat
- pandas

2.2 Verified project maturity
-----------------------------

The current v1 implementation is not a prototype consisting only of stubs.

It has been fully implemented and verified with:

- Resolver logic for slugification, Wikipedia direct resolution, search, redirects,
  disambiguation handling and missing-page handling.
- Bronze ingestion against live Wikipedia and GBIF APIs.
- Explicit raw-response persistence.
- Pydantic validation for all three source contracts.
- Explicit rejection reasons.
- Wikipedia-pivot merge behavior.
- GBIF taxonomy augmentation.
- GBIF occurrence aggregation.
- DuckDB UPSERT logic.
- Species catalog management.
- Canonical Species model.
- Semantic section-based chunking.
- Local embedding generation.
- FAISS vector indexing.
- Structured retrieval filters.
- End-to-end orchestration.
- Idempotency verification.
- Retry with exponential backoff for Wikipedia rate limits.
- Seed, ad-hoc and mixed-batch processing.

The existing verification baseline reached:

    201 / 201 tests passing

A complete run with all 18 seed species produced approximately:

    18 valid Wikipedia species
    18 valid GBIF taxonomy records
    484 valid GBIF occurrences
    416 rejected GBIF occurrence records

    149 semantic chunks
    149 FAISS vectors

This verified behavior is treated as functional capital and should be preserved whenever

5. ARCHITECTURAL PRINCIPLES
===========================

The v2 architecture SHALL follow these principles:

1. Preserve proven domain behavior.
2. Replace infrastructure, not validated business logic.
3. Keep the implementation Python-first.
4. Keep notebooks thin.
5. Use Delta managed tables as the persistence foundation.
6. Use Unity Catalog for logical organization and governance.
7. Keep Bronze reconstructable and append-only.
8. Use Silver as the validation and data-quality boundary.
9. Use Gold as the consumer-oriented knowledge product.
10. Prefer deterministic natural keys over generated surrogate keys.
11. Make idempotency content-aware.
12. Preserve rejection reasons and lineage.
13. Avoid unnecessary platform features during initial migration.
14. Do not introduce Lakeflow Spark Declarative Pipelines until the basic Delta design
    is working and understood.
15. Do not redesign working Python code unless the current behavior conflicts with
    the target lakehouse model.
16. Preserve KISS: extensibility without present over-design.


6. DATABRICKS DESIGN ALIGNMENT
==============================

The target follows the Databricks Medallion Architecture pattern:

    Bronze -> raw data
    Silver -> validated/refined data
    Gold   -> business/project-ready data products

Databricks describes Medallion as a logical data design pattern in which structure,
quality and reliability increase progressively between layers.

The architecture uses:

    Catalog:
        shark_knowledge

    Schemas:
        shark_knowledge.bronze
        shark_knowledge.silver
        shark_knowledge.gold

A separate catalog per medallion layer is not required.

9. GLOBAL DATA CONVENTIONS
==========================

9.1 species_key
---------------

species_key remains the canonical species identifier.

It is generated deterministically:

    species_key = slugify(scientific_name)

Example:

    "Prionace glauca" -> "prionace_glauca"

The universe of species remains open.

Seed species are demonstration inputs, not an access-control list.


9.2 run_id and batch_id
-----------------------

batch_id identifies a logical requested batch.

run_id identifies one physical execution.

Example:

    batch_id = "seed_batch_01"

    first execution:
        run_id = UUID-A

    second execution:
        run_id = UUID-B

This permits repeated execution of the same batch while retaining operational auditability.


9.3 content_hash
----------------

Silver and Gold records SHALL use a deterministic SHA-256 content hash.

The hash SHALL be calculated from a canonical representation of business fields.

Operational fields SHALL NOT affect the hash.

Excluded examples:

- run_id
- validated_at
- load timestamp
- last execution timestamp

Included fields are the data values whose semantic change must propagate downstream.

Canonical serialization SHALL use:

- UTF-8.
- Stable field ordering.
- Stable NULL representation.
- Deterministic list ordering where order is semantically defined.

The Delta update rule is:

    natural key exists AND content_hash changed
        -> UPDATE

    natural key exists AND content_hash unchanged
        -> NO OP

    natural key does not exist
        -> INSERT


9.4 Logical constraints
-----------------------

Primary keys documented in this SAS are logical business constraints.

Idempotency SHALL be enforced by pipeline logic and Delta MERGE semantics.

The design does not depend on Databricks enforcing uniqueness constraints physically.


10. BRONZE LAYER
================

10.1 Purpose
------------

Bronze represents the exact source observations obtained during ingestion.

Bronze is:

- append-only;
- reconstructable;
- audit-oriented;
- minimally transformed;
- not semantically validated.

Errors are data.

HTTP errors, empty responses and source anomalies SHALL be persisted whenever a request
produces an observable response/result.


10.2 Raw payload representation
-------------------------------

raw_payload SHALL initially use STRING containing the complete raw JSON/envelope.

Reason:

- Bronze's primary responsibility is faithful capture.
- Existing Python fetchers already produce JSON envelopes.
- Silver owns semantic parsing and validation.
- The project does not currently require complex Bronze-level semi-structured queries.

VARIANT may be evaluated in a later revision if Bronze querying requirements justify it.

11. SILVER LAYER
================

11.1 Validation strategy
------------------------

Existing Pydantic v2 contracts SHALL be retained during the first Databricks migration.

The validation flow becomes:

    Bronze Delta
        |
        v
    Python deserialize
        |
        v
    Pydantic validation
        |
        +--> valid ------> Silver Delta
        |
        +--> invalid ----> silver.rejected_records

Pydantic remains the executable Python contract.

Delta becomes the persistence contract.

Lakeflow Expectations are explicitly deferred and MAY later replace or complement
selected validation rules.


11.2 silver.wikipedia_pages
---------------------------

Logical primary key:

    species_key

Fields:

    species_key             STRING       NOT NULL
    title                   STRING       NOT NULL
    resolved_via            STRING       NOT NULL
    extract                 STRING       NOT NULL
    sections_text           STRING       NOT NULL
    page_url                STRING       NOT NULL
    is_disambiguation       BOOLEAN      NOT NULL
    source_ingestion_id     STRING       NOT NULL
    content_hash            STRING       NOT NULL
    validated_at            TIMESTAMP    NOT NULL

    REDIRECT

    PAGE_NOT_FOUND
    AMBIGUOUS_RESOLUTION
    EXTRACT_TOO_SHORT
    DISAMBIGUATION_PAGE
    HTTP_ERROR
    MISSING_SECTIONS_TEXT

Write semantics:

    MERGE ON species_key

    source.content_hash <> target.content_hash

11.5 silver.rejected_records
----------------------------

Purpose:

    unified quarantine and audit table for invalid records

Logical primary key:

    rejection_id

Fields:

    rejection_id            STRING       NOT NULL
    run_id                  STRING       NOT NULL
    batch_id                STRING       NOT NULL
    source                  STRING       NOT NULL
    species_key             STRING       NULL
    natural_key             STRING       NULL
    rejection_reason        STRING       NOT NULL
    rejection_detail        STRING       NULL
    record_payload          STRING       NOT NULL
    record_hash             STRING       NOT NULL
    source_ingestion_id     STRING       NULL
    rejected_at             TIMESTAMP    NOT NULL

rejection_id SHALL be deterministic.

Recommended calculation:

    SHA256(
        source
        + natural/business key
        + rejection_reason
        + record_hash
    )

Purpose:

    repeated processing of the same invalid logical record SHALL NOT create uncontrolled
    duplicate quarantine records.

Write semantics:

    MERGE ON rejection_id


12. KNOWLEDGE INTEGRATION RULES
===============================

The physical Merge layer is removed.

The existing merge/merger.py business logic remains and becomes the transformation
between Silver and Gold.


12.1 Wikipedia pivot
--------------------

Wikipedia remains mandatory.

A species without a valid Silver Wikipedia page SHALL NOT be inserted into Gold.

GBIF SHALL NOT independently introduce a species into Gold.


12.2 GBIF taxonomy augmentation
-------------------------------

Taxonomy is joined by species_key only when:

    match_type == EXACT

When taxonomy is not available/valid:

    taxonomy_status = UNMATCHED

The species may remain valid because Wikipedia is the mandatory pivot.


12.3 GBIF occurrence aggregation
--------------------------------

Valid occurrence rows SHALL be aggregated by species_key.

Required derived fields:

    n_valid_occurrences
    countries
    year_min
    year_max
    iucn_red_list_category

countries SHALL remain deterministically ordered according to the current project rule,
which orders countries by descending frequency.

IUCN mode/tie behavior SHALL preserve the existing deterministic implementation.

When zero valid occurrences exist:

    augmentation_status = GBIF_AUGMENTATION_EMPTY

This is not a fatal error.

14. CHUNKING CONTRACT
=====================

14.1 Semantic strategy
----------------------

The existing semantic section-first strategy is preserved.

Canonical sections remain:

    Identity
    Taxonomy
    Morphology
    Distribution
    Habitat
    Behavior
    Diet
    Reproduction
    Conservation
    Human Interaction
    References
    Multimedia


14.2 Evolution from v1
----------------------

v1 effectively used:

    one non-null canonical section -> one chunk

v2 SHALL use:

    canonical section
        |
        +--> sufficiently small -> one chunk
        |
        +--> too large ----------> N deterministic subchunks

Fixed-size chunking without semantic section context is not adopted.


14.3 chunk_id
-------------

chunk_id remains deterministic.

Format:

    {species_key}__{section}__{ordinal:03d}

Examples:

    carcharodon_carcharias__habitat__001
    carcharodon_carcharias__habitat__002


14.4 Initial size bound
-----------------------

Initial design bound:

    MAX_CHUNK_BYTES = 24_000

Measured as:

    len(text.encode("utf-8"))

The margin is deliberately conservative to leave room for future AI Search embedding
source-column limits.

Chunk splitting SHALL preserve deterministic ordering.


15. IDEMPOTENCY MODEL
=====================

v2 explicitly distinguishes raw-history idempotency from logical-state idempotency.


15.1 Bronze
-----------

Bronze is append-only.

Re-running the same logical batch may produce new raw observations.

This is allowed and desirable because Bronze is an ingestion audit trail.


15.2 Silver
-----------

For an identical logical source state:

    zero new logical records
    zero unnecessary updates

A record is updated only when the content hash changes.


15.3 Gold
---------

For an identical Silver state:

    zero new Species
    zero new SpeciesChunks
    zero unnecessary updates
    zero content_hash changes

This makes downstream synchronization content-aware.


15.4 New idempotency definition
-------------------------------

For the same logical state of the sources, repeated executions may append new Bronze
observations but MUST converge to the same logical Silver and Gold state.

    populated Silver Delta tables
    exactly 18 accepted gold.species rows
    one or more deterministic chunks per accepted Species


19.2 Rerun
----------

Running the same logical seed set again produces:

    Gold new Species              = 0
    Gold new SpeciesChunks        = 0
    Gold content hash changes     = 0

Silver MUST similarly avoid logical duplicates.


19.3 Ad-hoc species
-------------------

A species outside the seed set can be requested using only its scientific name.

The pipeline resolves and processes it through:

    Bronze
        -> Silver
        -> Gold

without editing a master allow-list.

origin SHALL be:

    AD_HOC


19.4 Quarantine
---------------

A species with invalid Wikipedia resolution SHALL NOT enter Gold.

The rejection SHALL remain inspectable in:

    shark_knowledge.silver.rejected_records


19.5 GBIF tolerance
-------------------

Invalid or missing GBIF augmentation SHALL NOT invalidate an otherwise valid Wikipedia
species.

The corresponding status SHALL remain explicit.


20. FUTURE AI SEARCH PHASE
==========================

AI Search is intentionally deferred until Data Ready.

The planned serving architecture is:

    shark_knowledge.gold.species_chunks
        |
        v
    Databricks AI Search Delta Sync Index

Gold is the knowledge-base source of truth.

The AI Search index is a derived serving representation.

Therefore:

    Gold != vector index

Instead:

    Gold Delta table
        -> synchronized search index

This separation allows the index to be rebuilt without losing the knowledge base.


20.1 Planned source contract
----------------------------

Future source table:

    shark_knowledge.gold.species_chunks

Planned primary key:

    chunk_id

Planned embedding source column:

    text

Planned source URI:

    document_uri

Planned metadata filters include:

    kingdom
    phylum
    class_name
    rank
    taxonomy_status
    iucn_red_list_category
    countries
    year_min
    year_max
    augmentation_status


20.2 Planned synchronization mode
---------------------------------

The preferred initial AI Search strategy is:

    Delta Sync
    Triggered synchronization

Reason:

    the current ingestion architecture is naturally batch-oriented.

Free Edition does not support Direct Vector Access, reinforcing the Delta Sync decision.


20.3 Row tracking / change feed preparation
-------------------------------------------

gold.species_chunks SHOULD be created with row tracking enabled to support future
incremental change processing.

Example target table property:

    delta.enableRowTracking = true

If the future AI Search configuration requires an explicitly materialized change data feed
for the chosen runtime/workspace configuration, it SHALL be enabled at implementation
time.

This SAS does not make the retrieval layer a prerequisite for the Data Ready milestone.


21. KNOWLEDGE ASSISTANT PHASE
=============================

Knowledge Assistant remains the long-term consumer of the Databricks-managed knowledge
source.

Target conceptual flow:

    gold.species_chunks
        -> AI Search Index
        -> Knowledge Source
        -> Knowledge Assistant

Knowledge Assistant is not supported by Databricks Free Edition as of this SAS revision.

Therefore it SHALL NOT constrain the first Data Ready implementation beyond low-cost
forward-compatible fields such as:

    document_uri
    chunk_id
    text
    retrieval metadata


22. MIGRATION STRATEGY
======================

The migration SHALL be incremental and conservative.


Phase 1 - Databricks setup

    Create catalog and schemas.
    Verify serverless notebook execution.
    Verify API outbound connectivity.


Phase 2 - Bronze migration

    Keep existing fetcher logic.
    Replace local JSON persistence with Bronze Delta append.
    Verify raw audit behavior.


Phase 3 - Silver migration

    Keep Pydantic models and validators.
    Replace valid/rejected JSON persistence with Delta tables.
    Implement deterministic rejection IDs.
    Implement content hashes.
    Implement MERGE behavior.


Phase 4 - Gold migration

    Reuse merger.py.
    Eliminate physical Merge and DuckDB stages.
    Populate gold.species.
    Adapt semantic chunking.
    Populate gold.species_chunks.
    Eliminate species_catalog and SpeciesMetadata persistence.


Phase 5 - Verification

    Run seed batch.
    Run identical seed batch again.
    Verify convergence.
    Run ad-hoc species.
    Verify quarantine cases.
    Confirm Data Ready acceptance criteria.


Phase 6 - Retrieval

    Only after Data Ready:
        create AI Search Delta Sync index
        verify retrieval and filters
        replace FAISS search behavior


Phase 7 - Agent

    Only in a supported Databricks environment:
        register AI Search as knowledge source
        configure Knowledge Assistant
        test grounded answers and citations


23. ARCHITECTURAL DECISIONS
===========================

ADR-V2-001
----------
Decision:
    Databricks Delta Lake + Unity Catalog replace local file persistence and DuckDB.

Rationale:
    Databricks becomes the system of record for medallion data.


ADR-V2-002
----------
Decision:
    Preserve custom Python API ingestion.

Rationale:
    Wikipedia and GBIF access patterns are domain-specific and already implemented.


ADR-V2-003
----------
Decision:
    Preserve Pydantic v2 validation for the initial migration.

Rationale:
    Existing contracts are tested and stable; replacing validation and storage
    simultaneously would add unnecessary migration risk.


ADR-V2-004
----------
Decision:
    Bronze uses Delta append-only raw tables.

Rationale:
    Raw history remains reconstructable and auditable.


ADR-V2-005
----------
Decision:
    Bronze raw payload is initially stored as STRING JSON.

Rationale:
    Maximum source fidelity and minimal ingestion transformation.


ADR-V2-006
----------
Decision:
    Silver uses current-state Delta tables with MERGE by natural key.

Keys:
    wikipedia_pages -> species_key
    gbif_taxonomy   -> species_key
    gbif_occurrences-> gbif_id


ADR-V2-007
----------
Decision:
    Use deterministic content_hash fields.

Rationale:
    Avoid meaningless updates and prepare for efficient downstream synchronization.


ADR-V2-008
----------
Decision:
    Consolidate all rejected records in silver.rejected_records.

Rationale:
    Central auditability without per-source filesystem structures.


ADR-V2-009
----------
Decision:
    Merge remains business logic but ceases to be a physical data layer.

Rationale:
    It is a Silver-to-Gold transformation, not a distinct data-quality tier.


ADR-V2-010
----------
Decision:
    Remove the DuckDB Warehouse stage.

Rationale:
    Delta managed tables already provide the persistent lakehouse storage layer.


ADR-V2-011
----------
Decision:
    gold.species replaces both species_merged and species_catalog.

Rationale:
    One canonical accepted-species product is sufficient.


ADR-V2-012
----------
Decision:
    SpeciesMetadata is no longer persisted separately.

Rationale:
    Retrieval metadata is denormalized into gold.species_chunks.


ADR-V2-013
----------
Decision:
    Preserve section-first semantic chunking.

Rationale:
    Canonical sections are meaningful knowledge boundaries.


ADR-V2-014
----------
Decision:
    Allow multiple chunks per canonical section.

Rationale:
    Long sections must remain compatible with downstream search/embedding limits.


ADR-V2-015
----------
Decision:
    Use 24,000 UTF-8 bytes as the initial maximum text chunk size.

Rationale:
    Conservative future compatibility margin for AI Search.


ADR-V2-016
----------
Decision:
    Retire local BGE embeddings and FAISS in the target runtime.

Rationale:
    Databricks AI Search will become the retrieval-serving technology.


ADR-V2-017
----------
Decision:
    Gold remains the knowledge-base source of truth; AI Search is derived.

Rationale:
    Search indexes must remain rebuildable.


ADR-V2-018
----------
Decision:
    Future AI Search uses Delta Sync rather than Direct Vector Access.

Rationale:
    Fits batch synchronization and Free Edition constraints.


ADR-V2-019
----------
Decision:
    Knowledge Assistant is deferred.

Rationale:
    The immediate engineering objective is correct, governed data; additionally,
    Free Edition currently does not support Knowledge Assistant.


ADR-V2-020
----------
Decision:
    Lakeflow Spark Declarative Pipelines are deferred.

Rationale:
    First migration should isolate the storage/platform change from an orchestration
    paradigm change.


ADR-V2-021
----------
Decision:
    Notebooks remain thin.

Rationale:
    Domain logic stays testable in Python modules.


ADR-V2-022
----------
Decision:
    Existing 201 tests are a behavioral baseline, not a fixed v2 test-count target.

Rationale:
    Tests tied only to retired local technologies must be replaced rather than preserved.


24. RISKS AND CONSIDERATIONS
============================

24.1 Outbound internet
----------------------

Free Edition restricts outbound internet access by default.

Wikipedia and GBIF connectivity must be tested from the actual workspace.

This is an operational constraint, not a reason to redesign the medallion contracts.


24.2 Free Edition quotas
------------------------

The project must remain small and educational.

The 18-species seed dataset is appropriate for demonstration and verification.


24.3 Hash canonicalization
--------------------------

Hashing must be stable across executions.

Any change to canonical serialization rules is a data-contract change.


24.4 Chunk evolution
--------------------

Changing the chunking algorithm can change chunk IDs and therefore retrieval identity.

Chunking versioning may be introduced later if substantial algorithm changes are required.


24.5 Source volatility
----------------------

Wikipedia and GBIF are external systems.

Bronze history is intentionally preserved so source changes can be audited and downstream
data rebuilt.


24.6 Knowledge Assistant availability
-------------------------------------

The future Knowledge Assistant phase depends on Databricks feature availability,
workspace tier and region at implementation time.

The Gold contracts should remain usable independently of that feature.


25. DEFINITION OF SUCCESS
=========================

Shark Knowledge v2 is successful when:

1. The existing domain behavior is preserved.
2. No local warehouse is needed.
3. No local vector store is needed for the target architecture.
4. Bronze, Silver and Gold are persisted as governed Delta tables.
5. Raw source responses remain auditable.
6. Invalid records remain explicitly explainable.
7. Reprocessing converges deterministically.
8. New species can enter without modifying a closed master list.
9. Gold exposes a canonical Species product.
10. Gold exposes an AI-search-ready SpeciesChunks product.
11. The design remains simple enough to run and study in Databricks Free Edition.
12. AI Search and Knowledge Assistant can be added without redesigning the Gold model.

27. SOURCE PROJECT BASELINE
===========================

This SAS supersedes the local-runtime architecture decisions of Shark Knowledge v1
while preserving its validated domain rules.

Key v1 concepts retained:

- Species as the business entity.
- scientific-name-driven open species universe.
- deterministic species_key.
- Wikipedia English as mandatory descriptive pivot.
- GBIF Species Match as taxonomy augmentation.
- GBIF Occurrence as geographic/conservation augmentation.
- strict EXACT taxonomy matching.
- explicit quarantine.
- deterministic occurrence aggregation.
- 12-section Canonical Knowledge Model.
- section-based semantic Parent-Child chunking.
- explicit provenance.
- idempotency.
- auditability.
- seed / ad-hoc processing.

Key v1 implementation mechanisms retired:

- local Bronze JSON files as primary persistence.
- individual Silver JSON valid/rejected files.
- DuckDB warehouse.
- species_catalog as an independent table.
- local sentence-transformers runtime.
- BAAI/bge-small-en-v1.5 as an architecture requirement.
- FAISS IndexHNSWFlat.
- FAISS metadata parquet.
- Docker Compose as the primary runtime topology.
